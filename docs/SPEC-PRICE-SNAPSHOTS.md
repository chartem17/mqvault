# SPEC — знімки цін для Market (запит до першого агента)

Дата: 2026-10-31. Основа: `7a1ea52e59b8ff7b1b5916ea88d22dff9db3a2a0` (`feat/undo-delete-current`).
Автор: другий агент. Це **специфікація-пропозиція**, а не міграція і не код. Схема БД, міграції, RLS, планувальник і секрети залишаються за першим агентом; нічого з цього документа не застосовано.

Позначки: **[факт]** — перевірено в коді або на сторінці провайдера; **[пропозиція]** — моя рекомендація, відкрита до змін; **[питання]** — потрібне рішення власника або першого агента.

## 1. Навіщо

Вкладка Market має показувати найсильніші й найслабші інструменти **за період** (день / тиждень / місяць) і давати фільтр за ринками. Власнику потрібна лише ціна, без свічок.

**[факт]** Провайдер без свічок віддає зміну лише за поточну добу. Для тижня й місяця потрібна ціна на початку періоду, тож її треба зберігати самим. Той самий масив цін дає «силу валют» (USD, EUR, GBP, JPY, AUD, NZD, CAD, CHF) за 28 парами.

## 2. Обмеження, які визначають дизайн

**[факт]** Twelve Data, безкоштовний Basic (сторінка тарифів, 2026-10-31):
- 8 кредитів на хвилину, 800 на добу; `/price` і `/quote` коштують **1 кредит за символ** (документація).
- Тож 28 форекс-пар за один цикл = 28 кредитів: це понад ліміт хвилини, а добовий ліміт дає ~28 повних циклів на добу.
- Ліцензія Basic названа «Internal non-display usage»; «Internal display data access» починається з плану Grow ($79/міс). Що саме означає «display» на практиці, не з'ясовано **[питання]**.

**[факт]** Binance (крипта) безкоштовний, оновлюється часто; Twelve Data для крипти не потрібен.

**[факт]** Знімки навмисно залежать від частоти опитування: чим рідше джерело, тим грубіший «початок періоду». Для тижня й місяця це не проблема.

## 3. Пропозиція зберігання **[пропозиція]**

Спільна довідкова таблиця (не користувацькі дані), умовна назва `market_price_snapshots`:

| Поле | Тип | Примітка |
|---|---|---|
| `symbol` | text, NOT NULL | значення `MarketInstrument.symbol` (наприклад `EURUSD`, `BTCUSDT`) |
| `bucket_at` | timestamptz, NOT NULL | початок вікна запису, наприклад година; разом із `symbol` — унікальний ключ, щоб повторний запуск не дублював |
| `captured_at` | timestamptz, NOT NULL | коли фактично отримано ціну |
| `price` | numeric, NOT NULL | точне значення; як віддавати його в API (рядок чи число) — за поточною угодою про numeric |
| `provider` | text, NOT NULL | `binance` / `twelve-data` / `derived` |
| `quality` | text, NOT NULL | `direct` або `derived` (синтетична крос-ціна, див. п. 5) |

- **Ключ і ідемпотентність:** `UNIQUE(symbol, bucket_at)`, запис через upsert; пізніший запуск у тому ж вікні не створює дубль.
- **Без `user_id`:** це ринкові дані, а не дані користувача. Читання лише через серверний клієнт; публічного доступу з анонімного ключа не потрібно.
- **Обсяг:** ~87 символів × 24 знімки/добу — це лише ~2 100 рядків на добу, ~190 тис. за 90 днів **[розрахунок]**.
- **Зберігання:** щогодинні знімки 90 днів + денний «закритий» знімок без обмеження терміну (потрібен для місяця й історії) **[питання]**.

Усе це — лише контракт-побажання. Фактичні типи, індекси, політики RLS і grants визначає перший агент.

## 4. Хто пише знімки **[питання]**

Потрібен фоновий запис без відкритої вкладки. Варіанти, жоден не обрано:
1. `pg_cron` у Supabase + Edge Function.
2. Cron хостингу застосунку (залежить від того, де він розгорнутий — зараз невідомо).
3. Планувальник GitHub Actions (безкоштовний, але мінімум 5 хв і без гарантії точності).

Вимоги до будь-якого варіанта:
- запис виконується лише на сервері з серверним ключем; жодного шляху запису з клієнта;
- рахує і зберігає тільки відповіді провайдера, **без демо-значень і без заповнення пропусків вигаданими цінами**;
- пропущений запуск залишає пропуск у даних, а не дублікат попереднього знімка.

## 5. Крос-пари через USD **[пропозиція]**

Щоб вкластись у ліміт кредитів, достатньо опитувати 7 пар із USD (EURUSD, GBPUSD, AUDUSD, NZDUSD, USDJPY, USDCAD, USDCHF) і обчислювати 21 крос як відношення (наприклад, `EURGBP = EURUSD / GBPUSD`).
- 7 кредитів на цикл замість 28: добовий ліміт 800 дає ~114 циклів (≈ раз на 12–13 хв цілодобово).
- Такі ціни — розрахункові: у них немає власного bid/ask, і вони можуть відрізнятися від брокерських на спред. Для рейтингу сили це допустимо; у БД вони мають бути позначені `quality = derived`, а в інтерфейсі — як розрахункові.
- Рішення залежить від вибору провайдера й тарифу **[питання]**; якщо тариф дозволяє 28 прямих запитів, розрахунок не потрібен.

## 6. Як рахувати період **[пропозиція]**

Зміна за період = `(остання − на початку) / на початку × 100`.

- **Вікно:** для v1 рекомендую ковзні 24 год / 7 діб / 30 діб, бо вони не залежать від часового поясу й моменту закриття дня. Календарні періоди (від 00:00 Kyiv або від відкриття тижня) вимагають явних налаштувань часового поясу й моменту переходу дня — як у prop-модулі; це **[питання]**.
- **Початкова ціна** — знімок найближчий до початку вікна, не пізніший за допуск (наприклад, 2 години для D/W/M). Якщо такого знімка немає, показується «—», а не оцінка.
- **Свіжість:** якщо останній знімок старший за порогове значення (наприклад, 3× інтервалу опитування), інструмент позначається `stale` і не береться в рейтинг (така сама логіка, як у PR #15 для котирувань у реальному часі).
- **Вихідні:** форекс і метали не торгуються; відсутні знімки у вихідні — норма, а не помилка.

**Сила валют** (**[пропозиція]**): для кожної з 8 валют — середнє арифметичне зміни за період по всіх її парах серед 28; у парі, де валюта є другою, знак змінюється на протилежний. Використовуються лише пари з повними даними на обидва кінці вікна. Формулу потрібно узгодити з власником **[питання]**.

## 7. Контракт API для Market **[пропозиція]**

Новий серверний роут (назва умовна) віддає на кожен інструмент: поточну ціну (з наявного шляху), `changePercent` за обране вікно, `basis` (`provider_day` або `snapshot`), `baselineAt`, `quality`, `stale`. Для відсутніх даних поля `null`, а не нулі. Назви полів DB ↔ UI узгоджувати явним адаптером, як у решті проєкту.

## 8. Критерії готовності

1. Міграція (за рішенням першого агента) застосована; повторний запуск запису в тому ж вікні не створює дублів.
2. Після ≥ 7 днів роботи Market показує зміну за 7 діб із правильним `baselineAt`; для інструментів без базового знімка видно «—».
3. Для 24 год / 7 діб / 30 діб значення збігаються з ручним розрахунком за двома-трьома символами на тестових знімках.
4. Свідомо вимкнений провайдер дає `stale`/пропуск, а не стару ціну без позначки.
5. Жоден шлях клієнта не може записати в таблицю; читання лише через сервер.
6. Автоматичний тест чистої функції періодів (початкова ціна, пропуски, вихідні, DST-межі, відсутній знімок) і сили валют.
7. Перевірено в браузері з перезавантаженням; якщо чогось не запускали — прямо вказано.

## 9. Відкриті питання

**Власнику:**
1. Ковзні вікна (24 год / 7 діб / 30 діб) чи календарні (від 00:00 Kyiv, від відкриття тижня)?
2. Прийнятна затримка форекс-цін ≈ 12 хв за безкоштовним тарифом, чи потрібна платна підписка (Twelve Data Grow, $79/міс, за сторінкою тарифів)?
3. Чи потрібні сила валют і фільтр за ринками одразу, чи спочатку лише рейтинг?
4. Чи використання Basic для власного приватного дашборда прийнятне за умовами ліцензії? Рекомендую уточнити в підтримці Twelve Data.

**Першому агенту:**
1. Де розгорнуто застосунок і який планувальник доступний?
2. Чи згоден з обсягом і ключем таблиці, терміном зберігання?
3. Як передавати numeric у відповідях API (рядок чи число) для цих цін?
4. Чи потрібен окремий тип, чи розширити загальний згенерований `database.types.ts`, коли він з'явиться?

## 10. Що не входить

Свічки, історія понад зберігання, сповіщення, торгові сигнали, виведення «що торгувати» — лише ціна й зміна за період. Акції з Market прибрано (PR #15), як і форекс-екзотику.
