- [ ] Завершити приймальну перевірку на окремих тестових записах: кілька одночасних плашок, скасування, перезавантаження до таймера, мережеві помилки, повторне завантаження та збереження інших рахунків.

Поточна модель — відкладене остаточне видалення, НЕ soft delete і НЕ кошик. Після завершення таймера повернення вже видаленого запису не гарантується. Закриття/перезавантаження до таймера скасовує невідправлений запит; втрата відповіді після відправлення потребує звірки з сервером.

- [ ] Скасування редагування угоди (історія змін або останній знімок) — окрема майбутня задача.

Soft delete, кошик і автоочищення через 30 днів не входять у поточну погоджену реалізацію. Повернути їх у план можна лише окремим рішенням.

## Етап 2. Проп-система — наступний пріоритет

### Погоджений принцип

Тип рахунку та спосіб отримання угод — дві незалежні настройки:

- Тип: «Особистий» або «Проп».
- Ведення/підключення: вручну або через MT5.

Підтримати всі чотири комбінації: особистий вручну, особистий MT5, проп вручну, проп MT5. Не визначати тип рахунку за платформою і не вважати будь-який MT5-рахунок пропом.

Проп-система вмикається лише за явним вибором користувача під час додавання рахунку. Умови користувач налаштовує сам; підключення MT5 не є обов'язковим і не підставляє вигаданих умов фірми.

### 2.1. Перший пакет — форма, збереження та перевірка даних

- [ ] Перевірити поточні UI/API/схему accounts та прибрати залежність account_type від manual/MT5.
- [ ] Додати до створення рахунку явний вибір «Особистий / Проп» незалежно від способу ведення.
- [ ] Для особистого рахунку залишити просту форму без обов'язкових проп-полів і проп-віджетів.
- [ ] Лише після вибору «Проп» показувати додатковий блок: розмір/початковий капітал рахунку, ціль прибутку, максимальний загальний збиток, денний ліміт, мінімум торгових днів, поточна фаза або Funded.
- [ ] Явно зберігати одиниці лімітів та базу розрахунку; не змішувати відсотки із сумами. Невстановлена умова означає «не задано», а не автоматичне порушення чи вигаданий ліміт.
- [ ] Додати потрібні поля без руйнівної міграції та без автоматичної перекласифікації наявних рахунків за платформою.
- [ ] Зберігати й повертати налаштування через API/Supabase; перевіряти числові значення, типи й власника на сервері.
- [ ] Вибір поточної фази — властивість одного рахунку, без автоматичного створення інших рахунків або перенесення угод.
- [ ] Перевірити весь пакет разом: чотири комбінації тип/ведення, перемикання форми, збереження, оновлення сторінки, помилки валідації та відсутність впливу на інші рахунки.

### 2.2. Другий пакет — прогрес і ліміти обраного проп-рахунку

- [ ] Target progress, Max loss used, Daily limit і торгові дні рахувати з умов, які задав користувач.
- [ ] Проп-показники показувати лише в контексті відповідного проп-рахунку; не переносити їх на особисті рахунки чи змішаний All accounts view як загальний проп-ліміт.
- [ ] Погодити точні формули: balance/equity, статичний/trailing drawdown, базове значення, часовий пояс і момент скидання денного ліміту, правило підрахунку торгового дня.
- [ ] Спочатку реалізувати лише режими, для яких є достовірні дані. Без історії/поточних даних equity не показувати equity-ліміт чи trailing drawdown як точно перевірений; явно показувати обмеження або недоступність режиму.
- [ ] Перевірити ручний та MT5-рахунок на однакових тестових даних; відсутні умови відображати як «не задано».

### Пізніше, лише після перевірки потреби

- [ ] Оцінити користь зв'язування Phase 1 → Phase 2 → Funded. Це НЕ частина першого пакета й не обов'язкова можливість продукту.
- [ ] Якщо потреба підтвердиться — окремо спроєктувати групи рахунків, parent_account_id та поведінку переходів без змішування історії.
- [ ] Перевірені шаблони проп-фірм можуть стати зручним доповненням до ручного налаштування. Автопідтягування умов не є вимогою першої версії.

## Правила виконання

- Зберігати робочий дизайн і не включати непов'язані переробки.
- Працювати в окремій погодженій гілці; існуючий баг видалення рахунків не приховувати й не закривати без доказів.
- Пов'язаний пакет доводити до цілісного стану, потім виконувати спільну автоматичну та особисту перевірку.
- Зміни БД, зовнішні записи й злиття в main — лише з окремим погодженням; реальні рахунки не використовувати для руйнівних тестів.
