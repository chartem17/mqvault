# Бекфіл початкового стопу, ризику й R (ADR 0020)

Кожен крок із записом у БД — лише після погодження власником саме цього кроку. Preview і production мають одну БД.

## Крок 0. Міграція
`supabase/migrations/20261116120000_trade_initial_risk.sql` — дві порожні колонки (`initial_stop_loss`, `risk_basis`) і check. Дані не змінює. Застосовується **до** злиття PR (новий код пише ці колонки).

## Крок 1. Подивитись, що зміниться (лише читання)
```bash
node scripts/backfill-trade-risk.mjs
```
Потрібні `NEXT_PUBLIC_SUPABASE_URL` і `SUPABASE_SECRET_KEY` у середовищі. Скрипт компілює ті самі `trade-financials.ts` і `deals-to-trades.ts`, що й застосунок, і друкує підсумок: скільки угод отримають початковий стоп із Bridge, скільки змінять net, розподіл `risk_basis`, скільки угод мали R до і матимуть після.

## Що можна відновити і як

| Угоди | Початковий стоп | Як |
|---|---|---|
| Синхронізовані Bridge (рахунок ACG, 28) | **точно**: стоп ордера відкриття з `bridge_orders` | скрипт, крок 2 |
| З MT5-звітів / внесені вручну на старих проп-рахунках (~285) | у БД — лише останній стоп; **точно** можна відновити, якщо MT5 ще пускає на ці рахунки (у т.ч. інвесторським паролем) | підключити рахунок через Bridge: він читає всю історію ордерів, прив'язує угоди до наявних (тикет або символ + час ± 1 хв + ціна) і заповнює порожній `initial_stop_loss`; потім крок 2 |
| Решта (рахунок закрито, історії немає) | не відновлюється | на вибір власника: (а) лишити без R від стопу — R лише там, де є введений ризик; (б) оцінка за плановим ризиком, крок 3 |

Чому не евристика «останній стоп = початковий, якщо угода збиткова»: стоп міг бути підтягнутий і до збитку; такий R виглядав би точним, але не був би ним.

## Крок 2. Записати (після погодження)
```bash
node scripts/backfill-trade-risk.mjs --apply
```
**Увага:** старі угоди без початкового стопу втратять R, який зараз рахується від останнього стопу (орієнтовно до 230 угод, точне число покаже крок 1; лишиться R там, де є введений ризик). Це чесно — той R був ненадійним, — але статистика за сетапами тимчасово стане біднішою. Тому спершу варто зробити підключення старих рахунків через Bridge (таблиця вище), а крок 3 вирішити разом із кроком 2.

Заповнює `initial_stop_loss` для Bridge-угод, перераховує `net_pnl` (виправляє 61 угоду #11718036 з невідніманою комісією, −$119.48 сумарно), `risk_amount`, `risk_percent`, `risk_basis`, `result_r` для всіх угод.

## Крок 3 (необов'язково). Оцінка за плановим ризиком
```bash
node scripts/backfill-trade-risk.mjs --planned-percent=1          # подивитись
node scripts/backfill-trade-risk.mjs --planned-percent=1 --apply  # записати
```
Для закритих угод без стопу й без введеного ризику: `risk_percent = 1`, `risk_amount = 1 % стартового балансу`, `risk_basis = 'planned'`, `R = net / risk_amount` (як на уроці). Позначка `planned` лишається, тож статистику можна фільтрувати «лише точний R». Відсоток називає власник.

## Перевірка після
```sql
select risk_basis, count(*), count(result_r) from journal_trades where closed_at is not null group by 1;
select count(*) from journal_trades where closed_at is not null and abs(net_pnl - (gross_pnl - abs(commission) - abs(fee) + swap)) > 0.005; -- очікується 0
```
