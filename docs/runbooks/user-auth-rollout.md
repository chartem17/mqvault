# Розгортання облікових записів (ADR 0017)

Перехід з одного пароля на акаунти Supabase Auth. **Порядок кроків обов'язковий:** якщо код потрапить у production раніше за кроки 1–3, увійти не зможе ніхто, зокрема власник. Preview користується тією самою БД, тому кроки 1–3 виконуються один раз на обидва середовища.

Кроки 1–3 і 6 змінюють БД або налаштування зовнішніх сервісів — кожен лише після погодження власника.

## 1. Supabase Auth (Dashboard → Authentication)

- **Sign In / Providers → Email:** увімкнено; **Confirm email — увімкнено** (обов'язково: на підтвердженій пошті тримаються запрошення і прив'язка власника); мінімальна довжина пароля — 10; за наявності тарифу — перевірка на злиті паролі.
- **URL Configuration:** Site URL = адреса production (те саме значення, що `VAULT_SITE_ORIGIN`). Redirect URLs: `https://<домен>/**`, для preview — `https://*-<команда>.vercel.app/**`, для локальної роботи — `http://localhost:3000/**`.
- **Email Templates** — щоб посилання працювало в будь-якому браузері (лист відкрили на телефоні, реєструвались на ПК), замінити посилання в шаблонах:
  - Confirm signup: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`
  - Reset password: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`
  - Change email address: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email_change`

  Без цього кроку листи теж працюють (через `/auth/callback`), але лише в тому браузері, де почали реєстрацію чи скидання.
- **SMTP:** вбудована пошта Supabase обмежена кількома листами на годину й годиться тільки для перевірки. Для бети підключити власний SMTP (окреме рішення: сервіс і домен).
- **Google (необов'язково):** створити OAuth-клієнт у Google Cloud, вписати Client ID і Secret у Providers → Google, додати адресу callback Supabase в дозволені redirect URI клієнта. Потім `NEXT_PUBLIC_AUTH_GOOGLE=1` у Vercel.

## 2. Міграція

Застосувати `supabase/migrations/20261109180000_user_auth.sql` (додає `app_users.auth_user_id`, `beta_invites`; забирає права в `anon`/`authenticated`). Даних не змінює. Поточний production (вхід паролем) після неї працює далі: він ходить у БД лише сервісним ключем.

Перевірка після застосування:

```sql
select count(*) filter (where is_owner) as owners, count(*) filter (where auth_user_id is not null) as linked from public.app_users;  -- 1, 0
select has_table_privilege('authenticated', 'public.journal_trades', 'select');  -- false
```

Advisors: очікувані INFO «RLS enabled, no policy» (тепер і для `beta_invites`).

## 3. Пошта власника

Рядок власника в `app_users` уже має пошту. Власник реєструється **саме з нею** — тоді його журнал прив'яжеться до нового акаунта під час першого входу. Якщо потрібна інша адреса, спершу змінити її (нижній регістр):

```sql
update public.app_users set email = '<нова адреса>' where is_owner;
```

Запрошення інших людей:

```sql
insert into public.beta_invites (email, note) values ('<адреса в нижньому регістрі>', '<хто це>');
```

## 4. Змінні середовища (Vercel: Production і Preview)

| Змінна | Значення |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | без змін |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | publishable-ключ проєкту (стара назва `NEXT_PUBLIC_SUPABASE_ANON_KEY` теж приймається) |
| `SUPABASE_SECRET_KEY` | без змін; ним також підписується cookie скидання пароля |
| `VAULT_SITE_ORIGIN` | адреса сайту, напр. `https://mqvault.vercel.app`; на неї ведуть листи. Для Preview не задавати — береться адреса самого деплою |
| `AUTH_SIGNUP_MODE` | не задавати (закрита бета). `open` — відкрита реєстрація, окреме рішення |
| `NEXT_PUBLIC_AUTH_GOOGLE` | `1` лише після налаштування Google |
| `VAULT_ACCESS_PASSWORD` | більше не використовується; видалити після кроку 6 |

## 5. Перевірка на Preview (до merge)

1. Відкрити preview-деплой гілки → має перекинути на `/login`.
2. «Створити акаунт» з поштою власника → лист → посилання → відкривається застосунок **з наявними угодами й рахунками**.
3. Меню акаунта (іконка в шапці): пошта правильна; «Вийти» повертає на `/login`; вхід паролем працює.
4. «Забули пароль?» → лист → новий пароль без запиту старого → вхід із новим.
5. Незапрошена адреса: реєстрація відповідає «лише за запрошенням».
6. Запрошена тестова адреса: після підтвердження — порожній журнал, вкладок «Ринок» і «Календар» немає, угод власника не видно. Створити рахунок і угоду, вийти, увійти власником — чужих даних немає.
7. Телефон і українська мова на сторінках входу.
8. MT5 Bridge на ПК власника продовжує синхронізуватись (пристрій прив'язаний до `app_users.id`, який не змінився).

Перевірка прив'язки:

```sql
select is_owner, auth_user_id is not null as linked from public.app_users order by created_at;
```

## 6. Merge і після нього

- Merge у `main` — рішення власника. Після деплою повторити пункти 1–3 кроку 5 на production.
- Видалити `VAULT_ACCESS_PASSWORD` з Vercel.
- Тестового користувача прибрати: видалити його рядок `app_users` (каскадом зникнуть його дані) і Auth-користувача в Dashboard.

## Відкат

Повернути попередній деплой у Vercel (Instant Rollback): старий код не залежить від нової колонки й таблиці, а `VAULT_ACCESS_PASSWORD` до кроку 6 ще на місці. Міграцію відкочувати не потрібно.

## Якщо щось пішло не так

| Симптом | Причина |
|---|---|
| Усі сторінки відповідають 503 «Sign-in is not configured» | немає `NEXT_PUBLIC_SUPABASE_URL` або publishable-ключа в цьому середовищі |
| Після входу — «Сервіс тимчасово недоступний» | міграцію не застосовано (немає `auth_user_id`) |
| Власник увійшов, але журнал порожній | зареєструвався з іншою поштою, ніж у `app_users`; створився новий простір. Виправлення — окрема погоджена дія в БД |
| «Посилання застаріло» одразу після листа | шаблони листів не замінено і лист відкрито в іншому браузері; або посилання вже використане (деякі поштові сервіси відкривають його самі під час перевірки) |
| Будь-яке збереження відповідає 403 «Same-origin JSON» | `VAULT_SITE_ORIGIN` не збігається з адресою, з якої відкрито сайт |
| Лист не приходить | ліміт вбудованої пошти Supabase; потрібен власний SMTP |
