# Проп-рахунки: умови та гілки етапів

Рішення і причини — [ADR 0004](../decisions/0004-prop-rules-simplified.md). Тут — як це працює. Ручна приймальна перевірка — [runbook](../runbooks/prop-acceptance-checklist.md).

Рішення (2026-11-05): **EOD/trailing і будь-які правила, специфічні для фірми, не підтримуються.** У різних фірм різні умови, і заповнювати їх надто довго. Лишилося:

- ціль прибутку, %
- загальний ліміт збитку, %
- денний ліміт збитку, %
- мінімум торгових днів
- необов'язкова фаза (Phase 1 / 2 / 3 / Funded) — позначка рахунку

## Умови: семантика
- Кожна умова має стан: `unknown` (не налаштовано), `not_applicable` (вимоги немає), `configured` (є значення).
- `legacy` значення без стану вважається налаштованим; порожнє — `unknown`, а не «вимоги немає».
- `not_applicable` ховає умову, але не стирає значення.
- Ліміти збитку зберігаються як ваші умови; застосунок їх не перевіряє й не виносить вердикт «пройдено/провалено».
- Funded — лише позначка етапу, а не шаблон правил.

## Редактор
GET/PATCH `/api/accounts/:id/prop-rules`; PATCH приймає `expectedRevision`, частковий `settings` і/або `phase`. Невідповідна ревізія дає 409. Невідомі поля відхиляються.

## Колонки в БД, які більше не використовуються
`prop_max_loss_mode`, `prop_day_timezone`, `prop_day_close`, `prop_loss_control_basis`, `prop_rules_notes` лишаються в таблиці `accounts` (порожні), але код їх не читає й не пише. Їх не видаляли: міграція адитивна, і видалення потребує окремого затвердження.

## Картка в Overview
Картка рахунку в Overview читає умови з `GET /api/accounts/:id/prop-rules` і редагує їх у діалозі. Деталі — розділ вище. Міграція `prop_rule_settings_v1` застосована раніше; без неї endpoint повертає 503 `schema_pending`.

## Гілки: Phase 1 → Phase 2 → Funded
Рахунки різні, але можуть бути звʼязані в одну лінійну гілку через наявну колонку `accounts.parent_account_id` («попередній етап»). Нової міграції немає.

- Привʼязка: поле «Попередній етап» у формі створення рахунку або в картці «Гілка рахунку».
- Серверні правила (`src/lib/accounts/account-api.ts`, `src/lib/accounts/account-chain.ts`): лише власні активні проп-рахунки; рахунок не може бути попереднім етапом сам для себе; без кіл; у етапу не більше одного наступного; зміна типу на особистий скидає привʼязку; видалення рахунку лише від'єднує сусідів (`permanent_entity_deletion`).
- Картка «Гілка рахунку»: етапи по порядку, у кожного net P&L, кількість угод і прогрес до власної цілі; внизу разом по гілці — net P&L, угод, торгових днів (у поясі користувача). Якщо в частині угод немає net P&L, сума показується як недоступна.
- Угоди й умови рахунків привʼязка не змінює. Автоматичних переходів між фазами й статусів pass/fail немає.
