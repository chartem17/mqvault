# MQVault Bridge — синхронізація угод MT5 з ПК користувача

**Статус:** проєкт (design), чекає погодження власника · **Дата:** 2026-11-08 · Рішення — [ADR 0015](../decisions/0015-mt5-desktop-bridge.md)

Мета: користувач завантажує інсталятор із сайту, запускає його, один раз натискає «Підключити» в браузері — і всі угоди з усіх терміналів MT5 на цьому ПК самі з'являються в журналі. Без паролів, без налаштувань MT5, без командного рядка, без відкритих портів.

Документ складається з трьох частин: **як це працює** → **доказ безпеки** (твердження → механізм → чим перевіряється) → **надійність**. Наприкінці — відкриті питання до власника та план робіт.

---

## 1. Чим це відрізняється від старого (вимкненого) мосту

Старий міст (вимкнено 2026-10-31, `f507917`) був локальним HTTP-сервером `127.0.0.1:8787`, до якого ходив сайт. Він працював лише коли сайт запущено на тому самому ПК, вимагав ручного запуску й відкривав порт на машині.

| | Старий міст | Новий Bridge |
|---|---|---|
| Напрям зв'язку | сайт → ПК (вхідні запити) | ПК → сайт (лише вихідний HTTPS) |
| Відкриті порти на ПК | так (8787) | **жодного** |
| Працює з production (Vercel) | ні | так |
| Запуск | вручну | автоматично при вході в Windows |
| Автентифікація | немає | ключ пристрою, кожен запит підписаний |
| Права в MT5 | — | лише читання історії; торгових викликів у коді немає |

Ендпоїнти `/api/mt5/*` лишаються «410 retired»; новий міст живе в окремому просторі `/api/bridge/*`.

## 2. Чому саме так (розглянуті варіанти)

| Варіант | Чому ні / так |
|---|---|
| **EA / Service на MQL5 у терміналі + `WebRequest`** | Користувач мусить додати URL у *Сервіс → Налаштування → Експерти → Дозволити WebRequest*, перетягнути EA на графік / запустити сервіс, увімкнути Algo Trading. Це саме ті «налаштування в терміналі», яких не має бути. Відхилено. |
| **Хмарний посередник (MetaApi тощо)** | Потрібен investor-пароль користувача на сторонньому сервері, платно за кожен рахунок, залежність від третьої сторони. Відхилено. |
| **Власні хмарні термінали** | Зберігання паролів, дорого, погано масштабується. Відхилено. |
| **Читати файли терміналу напряму** | Формат закритий і змінюється; ризик зламатись після оновлення MT5. Відхилено. |
| **Офіційний Python-пакет `MetaTrader5` у фоновій програмі на ПК** | Офіційний API MetaQuotes; підключається до **вже запущеного й залогіненого** терміналу через локальний IPC; читання історії не потребує жодних налаштувань терміналу й жодного пароля. **Обрано.** |

> Що треба підтвердити прототипом (етап 0): `initialize()` на чистій Windows без змін налаштувань у терміналах 3 різних брокерів; кілька терміналів одночасно; реакція антивірусів; ліцензія MetaQuotes на вбудовування пакета у розповсюджувану програму.

## 3. Як це працює

### 3.1. Компоненти

```
ПК користувача (сесія Windows користувача)                     Хмара
┌──────────────────────────────────────────────┐   HTTPS (лише вихідний)   ┌──────────────────────────────┐
│ terminal64.exe (MT5, вже залогінений)         │                           │ Vercel: /api/bridge/*        │
│        ▲ локальний IPC MetaQuotes (read-only)│                           │  • pairing (без входу)       │
│        │                                     │                           │  • device/* (підпис пристрою)│
│ mqvault-bridge.exe                            │ ── підписані запити ──▶ │  • approve (сесія власника)  │
│  • supervisor: знаходить термінали, рестарти │                           │            │                 │
│  • worker на кожен термінал: читає угоди      │ ◀── лише enum-статуси ── │            ▼                 │
│  • outbox (SQLite): черга до відправки        │                           │ Supabase (сервісний ключ)    │
│  • ключ пристрою (TPM / DPAPI)                │                           │  bridge_* , mt5_deals,       │
│  • трей-іконка: статус, «Відкрити журнал»     │                           │  journal_trades              │
└──────────────────────────────────────────────┘                           └──────────────────────────────┘
```

- **Програма:** Python 3.12 + офіційний `MetaTrader5`, зібрана в один `.exe` (Nuitka), підписана Authenticode.
- **Встановлення:** per-user інсталятор (Inno Setup, `PrivilegesRequired=lowest`) у `%LOCALAPPDATA%\MQVault\Bridge`. **Без прав адміністратора, без UAC, без служби, без драйвера.** Автозапуск — задача Планувальника «при вході користувача» з перезапуском при збої.
- **Чому не служба Windows:** IPC MetaTrader працює лише в тій самій сесії користувача, що й термінал; служба (сесія 0) до нього не дістається. Плюс: менше привілеїв.

### 3.2. Досвід користувача (вся «настройка»)

1. На сайті: *Налаштування → MT5 Bridge → Завантажити для Windows*.
2. Запустити `MQVaultBridge-Setup.exe` → «Встановити». Жодних питань, шляхів, галочок.
3. Інсталятор запускає Bridge; той сам відкриває браузер на `https://<сайт>/bridge/connect?code=K7Q2-M9XD`.
4. На сторінці: «Підключити комп'ютер **DESKTOP-7F3 (Windows-користувач artem)** до MQVault? Код: **K7Q2-M9XD** — той самий, що у вікні Bridge». Кнопка **Підключити**.
5. Готово. Bridge сам знаходить усі запущені MT5, підтягує всю історію й далі синхронізує щохвилини.

Крок 4 не прибираємо навмисно: це єдиний момент, коли людина в браузері (залогінена у свій журнал) підтверджує, що саме цей ПК може писати в її журнал. Без нього будь-хто, хто запустив інсталятор, міг би писати в чужий журнал.

### 3.3. Підключення пристрою (pairing) — за схемою OAuth Device Authorization (RFC 8628)

1. Bridge при першому запуску генерує пару ключів **ECDSA P-256**. Приватний ключ — у TPM (Microsoft Platform Crypto Provider), якщо його немає — неекспортовний ключ CNG / DPAPI (CurrentUser). Приватний ключ **ніколи не покидає ПК**.
2. `POST /api/bridge/pairings` `{public_key, device_name, os, bridge_version}` → `{pairing_id, user_code, expires_at}`. Публічний ендпоїнт, ліміт за IP.
   - `user_code` — 8 символів з алфавіту без схожих літер (32⁸ ≈ 10¹²), живе 10 хв, одноразовий, у БД лише його SHA-256.
3. Користувач на `/bridge/connect` (звичайна сесія сайту, same-origin) натискає «Підключити» → `POST /api/bridge/pairings/approve {user_code}` → створюється `bridge_devices` з `public_key` і `user_id` власника. Після 5 невдалих кодів — блок на 15 хв.
4. Bridge опитує `GET /api/bridge/pairings/{id}` **з підписом своїм ключем** — тобто забрати підтвердження може лише той, у кого приватний ключ, що був у запиті кроку 2. Відповідь: `device_id`.
5. З цього моменту всі запити Bridge — підписані (п. 3.4). Ніяких токенів-паролів, які можна вкрасти з диска чи трафіку й використати деінде, не існує.

### 3.4. Підпис кожного запиту

Заголовки: `X-MQV-Device: <device_id>`, `X-MQV-Seq: <лічильник>`, `X-MQV-Time: <unix ms>`, `X-MQV-Sig: <base64 ECDSA>`.

Підписується канонічний рядок:
```
mqv-bridge-v1\n<METHOD>\n<path>\n<time>\n<seq>\n<sha256(body) hex>
```
Сервер (`src/lib/bridge/signature.ts`, Web Crypto) перевіряє:
1. пристрій існує й не відкликаний;
2. `|now − time| ≤ 5 хв`;
3. підпис валідний для збереженого `public_key`;
4. **антиповтор:** атомарно `update bridge_devices set last_seq = $seq where id = $id and last_seq < $seq returning id` — якщо рядок не оновився, запит відхиляється. Навіть два однакові запити паралельно не пройдуть обидва.
5. тіло ≤ 2 МБ, строга схема.

### 3.5. Що Bridge читає і що відправляє

Читає (лише функції читання офіційного API): `account_info()`, `history_deals_get()`, `history_orders_get()` (початкові SL/TP — у deals їх немає, §9.1), `symbols_get()` + `copy_rates_range()` + `symbol_info_tick()` лише для видимих символів (зсув часу сервера, §9.3), пізніше — `positions_get()`.

Відправляє — **мінімум**:

| Поле | Навіщо |
|---|---|
| `server`, `login`, `company`, `trade_mode` (demo/real/contest), `currency` | зіставити з рахунком у журналі |
| `balance`, `equity` (у heartbeat) | показати баланс рахунку, проп-ліміти |
| угоди (deals): `ticket`, `order`, `position_id`, `time_msc`, `type`, `entry`, `symbol`, `volume`, `price`, `profit`, `commission`, `swap`, `fee`, `magic`, `reason` | побудувати угоди журналу |
| ордери позицій: `ticket`, `position_id`, `type`, `state`, `time_setup_msc`, `time_done_msc`, `price_open`, `sl`, `tp`, `volume_initial`, `reason` | початковий стоп → R; причина закриття |
| `server_offset_minutes` + момент вимірювання; час першого H1-бару кожного тижня | конвертація часу брокера в UTC (ADR 0001) |
| версія Bridge, коди помилок (без даних) | статус і підтримка |

**Не відправляє ніколи:** ім'я власника рахунку (`account_info().name`), пароль (Bridge його не бачить і не питає), вміст файлів терміналу, скріншоти, будь-що з інших програм. `comment` угоди — лише якщо власник вирішить (відкрите питання 4).

### 3.6. Сервер: з угод MT5 — угоди журналу

Bridge «тупий»: він лише пересилає сирі deals. Уся логіка — на сервері й тестується як інші модулі `src/lib`:

1. `POST /api/bridge/device/deals` → upsert у `mt5_deals` за `(device_account_id, deal_ticket)` — **ідемпотентно**, повтори безпечні.
2. `src/lib/bridge/deals-to-trades.ts`: групує deals за `position_id` (часткові закриття, реверси `inout`, комісії на вході й виході), час — `time_msc` брокера → UTC за `accounts.broker_timezone` (ADR 0001), net і R — `derivedFinancials` (ADR 0003, той самий код, що в CSV-імпорті).
3. Запис у `journal_trades` з `source = 'mt5'`, `ticket = position_id`, `meta.bridge = {device_id, synced_at}`.
4. **Що належить синхронізації, а що користувачу:** синхронізація оновлює лише фінансові поля (ціни, обсяг, час, gross/commission/swap, закриття). Сетап, емоції, нотатки, скріншоти, розбір (`meta.review`) — ніколи не перезаписуються. Видалену користувачем угоду (ADR 0005) синхронізація не воскрешає: тикет запам'ятовується як «ігнорувати».
5. Угода, вже внесена вручну або з CSV, розпізнається тими ж правилами дублікатів, що в ADR 0012 (тикет; або символ + напрямок + хвилина + ціна) — і **приєднується**, а не дублюється.

### 3.7. Зіставлення рахунку (без налаштувань)

- Є рівно один рахунок користувача з тим самим `login` + `server` → прив'язується автоматично.
- Немає → створюється рахунок `platform = mt5`, `account_type = personal`, назва «<company> · <login>», `broker_timezone` визначається з виміряного зсуву (п. 5.3). На Головній — плашка «Знайдено новий рахунок MT5: це проп? / не синхронізувати» — **завжди**, бо визначити проп автоматично неможливо: проп-рахунок ACG у MT5 має `trade_mode = demo` (§9.3).
- Кілька збігів → плашка «виберіть рахунок»; до вибору угоди лежать у `mt5_deals` і нікуди не пишуться.

## 4. Доказ безпеки

### 4.1. Що захищаємо (активи)

| Актив | Чому цінний |
|---|---|
| A1. Торговий рахунок MT5 (гроші) | найцінніше: зловмисник не повинен мати змоги торгувати чи виводити |
| A2. Пароль MT5 | дає повний доступ до рахунку |
| A3. ПК користувача | програма не повинна стати дверима в систему |
| A4. Журнал користувача на сайті | конфіденційність і цілісність даних |
| A5. Канал оновлень Bridge | хто ним керує — запускає код на всіх ПК користувачів |

### 4.2. Від кого (зловмисники)

- **Z1** — мережа (публічний Wi-Fi, провайдер, MITM).
- **Z2** — хтось в інтернеті, хто знає адресу сайту й API.
- **Z3** — зловмисник, що зламав сайт / Vercel / Supabase.
- **Z4** — зловмисник, що підмінив інсталятор / оновлення / залежність (supply chain).
- **Z5** — фішинг: змушує користувача підтвердити чужий пристрій.
- **Z6** — інша програма / інший Windows-користувач на тому ж ПК.
- **Z7** — шкідливе ПЗ з правами користувача на ПК (див. 4.5 — частково поза моделлю).

### 4.3. Твердження безпеки, механізми й перевірки

Кожне твердження має (а) механізм, (б) чому воно тримається, (в) тест/перевірку, без якої пакет не вважається готовим.

**S1. Bridge не може відкрити, змінити чи закрити угоду, навіть якщо його зламали віддалено.** (A1; Z2, Z3)
- *Механізм:* у коді немає жодного виклику торгових функцій (`order_send`, `order_check`, `order_calc_*` тощо). Доступ до `MetaTrader5` іде лише через модуль-обгортку `mt5_readonly.py`, який експортує 4 функції читання. Сервер **не має каналу команд**: відповідь на heartbeat — лише поля з фіксованого enum (`ok | resync | unlink | update_available`), будь-яке інше значення ігнорується. Немає `eval`, плагінів, завантаження коду, крім підписаного оновлення (S7).
- *Чому тримається:* щоб торгувати, потрібен код, який викликає `order_send`. Його немає в бінарнику, і сервер не може його туди доставити, бо доставка коду можлива лише через оновлення, підписане офлайн-ключем, якого немає на сервері.
- *Перевірка:* CI-тест — AST-сканування всього Python-коду: заборонені імена (`order_send`, `order_check`, `positions_close`, `eval`, `exec`, `__import__`, `importlib`, `subprocess`, `ctypes` поза модулем ключів) → збірка падає. Тест обгортки: `dir(mt5_readonly)` = рівно дозволений список. Тест клієнта: невідомий статус у heartbeat → нічого не відбувається.
- *Додатковий захист (опційно, не вимагається від користувача):* у MT5 є «Заборонити автоторгівлю через зовнішній Python API» — вмикає обмеження на рівні самого терміналу.

**S2. Bridge ніколи не бачить, не зберігає й не передає пароль MT5.** (A2; усі)
- *Механізм:* `initialize()` викликається **без** `login/password/server` — Bridge приєднується до терміналу, в який користувач уже увійшов сам. У коді немає полів для пароля, Bridge не читає файли терміналу (`accounts.dat`, `config/*`).
- *Перевірка:* AST-тест: виклик `initialize` лише з аргументом `path`; заборонені рядки `accounts.dat`, `password`. Сервер відхиляє будь-яке поле з `password|pass|secret` у тілі.

**S3. На ПК не з'являється нових вхідних точок атаки.** (A3; Z1, Z2, Z6)
- *Механізм:* Bridge не слухає жодного порту (ні TCP, ні localhost HTTP, ні named pipe з доступом для інших). Лише вихідний HTTPS на один хост сайту. Без прав адміністратора, без служби, без драйвера, файли в `%LOCALAPPDATA%` з ACL лише для поточного користувача.
- *Перевірка:* інтеграційний тест на Windows-runner: після запуску `Get-NetTCPConnection -State Listen -OwningProcess <pid>` порожній. Інсталятор перевіряється на відсутність запиту UAC і записів у `HKLM`.

**S4. Мережевий зловмисник нічого не читає й не підробляє.** (A4; Z1)
- *Механізм:* лише HTTPS (TLS 1.2+), перевірка сертифіката системним сховищем Windows, HSTS на домені; HTTP-редиректи не виконуються. Кожен запит підписаний (п. 3.4) і прив'язаний до хешу тіла, часу й лічильника.
- *Чому тримається:* навіть якщо TLS буде зламано (підкинутий кореневий сертифікат), перехоплений запит не можна змінити (підпис покриває тіло) і не можна повторити (лічильник), а приватного ключа в трафіку немає взагалі.
- *Перевірка:* тести `signature.ts`: змінене тіло / шлях / час / повторний `seq` / чужий ключ → 401. Тест клієнта: відмова на невалідний сертифікат і на `http://`.

**S5. Злам бази даних сайту не дає змоги видавати себе за Bridge користувача.** (A4; Z3)
- *Механізм:* у БД лише **публічні** ключі пристроїв і SHA-256 кодів підключення. Секретів, які можна вкрасти й використати, на сервері немає.
- *Перевірка:* рев'ю міграції: у `bridge_*` немає колонок з приватними ключами/токенами; тест: pairing зберігає лише хеш коду.

**S6. Пристрій може лише записувати угоди MT5 свого власника — і більше нічого.** (A4; Z2, Z5, Z7)
- *Механізм:* ендпоїнти `device/*` приймають лише: heartbeat, рахунки терміналу, deals. Читання журналу, налаштувань, інших рахунків, видалення — недоступні. `user_id` береться з `bridge_devices`, а не з тіла запиту. Межа: middleware пропускає без cookie **лише** точний префікс `/api/bridge/device/` і `POST /api/bridge/pairings`; все інше, включно з `approve`, — під звичайним входом.
- *Чому тримається:* навіть у найгіршому випадку — вкрадений ключ або фішингом підключений чужий ПК — зловмисник може лише **додати** фейкові угоди MT5 у журнал. Він нічого не прочитає й не видалить. Наслідок відновлюється: «Відкликати пристрій» + «Прибрати угоди цього пристрою» (видалення з Undo, ADR 0005).
- *Перевірка:* тест middleware-матриці: кожен шлях × (без cookie, з підписом, з cookie) → очікуваний статус. Тест: device A не може писати в рахунок користувача B (готується до багатокористувацької авторизації).

**S7. Оновлення не може поширити шкідливий код, навіть якщо зламано сайт або GitHub.** (A3, A5; Z3, Z4)
- *Механізм:* два незалежні підписи. (1) Authenticode-сертифікат на `.exe`. (2) Маніфест оновлення (`version, sha256, url`) підписаний **офлайн-ключем Ed25519 (minisign)**, який зберігається у власника поза Vercel/GitHub. Публічний ключ вшитий у Bridge. Bridge перевіряє підпис маніфесту → SHA-256 файлу → Authenticode-підписника → що версія новіша за поточну (захист від відкату) — і лише тоді атомарно замінює себе; якщо нова версія не пройшла самоперевірку за 2 хв — відкат на попередню.
- *Чому тримається:* зломщик сайту може підмінити файл на сервері, але не може зробити валідний підпис маніфесту без офлайн-ключа.
- *Перевірка:* тести апдейтера: невалідний підпис, чужий ключ, невідповідний хеш, старша версія, обрив завантаження → оновлення не застосовується, програма працює далі.

**S8. Ланцюжок постачання контрольований.** (A5; Z4)
- *Механізм:* збірка лише в GitHub Actions з тегу; залежності зафіксовані з хешами (`pip install --require-hashes`), мінімум залежностей (`MetaTrader5`, `cryptography`, без веб-фреймворків); SBOM (CycloneDX) і SHA-256 публікуються з кожним релізом; на сторінці завантаження — хеш і підписник.
- *Перевірка:* CI падає, якщо `requirements.lock` без хешів або з'явилась нова залежність без явного погодження.

**S9. Фішинг підключення не дає зловмиснику ні грошей, ні даних.** (Z5)
- *Механізм:* код живе 10 хв, одноразовий; сторінка підтвердження показує ім'я ПК, Windows-користувача, країну/IP пристрою й попереджає «Підтверджуйте лише якщо ви щойно встановили Bridge на цьому комп'ютері». Bridge сам відкриває сторінку з кодом — звичний сценарій не вимагає копіювати код звідкись.
- *Чому прийнятно:* за S6 підключений чужий пристрій може лише додавати угоди; нічого не читає. Новий пристрій показується в списку пристроїв і на Головній.

**S10. Локальні секрети не дістане інший Windows-користувач чи копія диска.** (Z6)
- *Механізм:* приватний ключ — у TPM (не можна скопіювати з ПК взагалі) або неекспортовний ключ CNG/DPAPI CurrentUser (прив'язаний до облікового запису Windows). Логи не містять ключів, підписів, угод — лише події й коди помилок.
- *Перевірка:* тест: у лог-файлах після повного циклу синхронізації немає `X-MQV-Sig`, тикетів і сум (grep у CI на фіктивних даних).

**S11. Сервер не довіряє даним Bridge.** (A4)
- *Механізм:* як у CSV-імпорті — строга схема, ліміти розміру й кількості, числа скінченні, символи ≤ 40 знаків, net/R рахує сервер (ADR 0003). Bridge — недовірений клієнт.
- *Перевірка:* fuzz-тести схеми (NaN, Infinity, мегарядки, від'ємні обсяги, дати 1970/2100).

### 4.4. STRIDE коротко

| Загроза | Де | Відповідь |
|---|---|---|
| Spoofing (підробка Bridge) | API | підпис ключем пристрою (S4, S5) |
| Tampering (зміна даних) | мережа, оновлення | підпис тіла (S4), підписані оновлення (S7) |
| Repudiation | журнал | `meta.bridge.device_id` на кожній угоді, список пристроїв з `last_seen` |
| Information disclosure | мережа, логи, БД | TLS, мінімум даних (3.5), без секретів у БД (S5) і логах (S10) |
| Denial of service | API | ліміти Vercel Firewall + розмір/частота на пристрій; DoS сайту не шкодить рахунку (дані чекають в outbox) |
| Elevation of privilege | ПК, API | без адміна й портів (S3); пристрій лише пише (S6); немає каналу команд (S1) |

### 4.5. Залишкові ризики — чесно

1. **Шкідливе ПЗ, яке вже працює з правами користувача на ПК (Z7),** може використати ключ пристрою (якщо не TPM) — але воно й так може керувати самим терміналом MT5 та браузером. Bridge цю ситуацію **не погіршує**: він не дає нічого, чого такий зловмисник не мав би без нього, а через ключ пристрою можна лише додати угоди в журнал.
2. **Якщо термінал залогінений майстер-паролем**, IPC MetaQuotes технічно дозволяє торгувати будь-якій локальній програмі. Bridge цього не робить (S1), але це властивість самого MT5, а не нашого коду. Рекомендація у FAQ: торгівлю через Python API в терміналі можна заборонити однією галочкою (необов'язково).
3. **Злам Authenticode-сертифіката разом з офлайн-ключем оновлень** — потрібні обидва; офлайн-ключ зберігається власником на окремому носії.
4. **Сайт поки однокористувацький (ADR 0006).** Прив'язка пристрою до `user_id` уже зроблена так, щоб пережити перехід на багатокористувацьку авторизацію, але тести міжкористувацької ізоляції стануть повними лише після неї.
5. **Доведення** тут — це аргумент «твердження → механізм → тест», а не формальна верифікація. Перед публічним запуском — незалежний пентест Bridge і API (пункт «безпека» в roadmap).

## 5. Надійність («просто працює»)

### 5.1. Життєвий цикл

- **Supervisor** раз на 15 с шукає процеси `terminal64.exe` (і `terminal.exe` у портативному режимі), бере шлях до exe. Сам **ніколи не запускає** термінал (`initialize(path)` викликається лише для вже запущеного процесу).
- На кожен термінал — окремий **worker-процес** (офіційний API дозволяє одне з'єднання на процес). Падіння worker'а не зачіпає інші; supervisor перезапускає з експоненційною затримкою (1 с → 5 хв).
- Supervisor сам під наглядом Планувальника завдань: «перезапускати при збої кожну хвилину, необмежено», плюс старт при вході в систему й після виходу зі сну.
- Термінал закрито → worker завершується тихо; відкрито знову → підхоплюється автоматично. Користувач переключив рахунок у терміналі → `account_info().login` змінився → синхронізується новий рахунок.

### 5.2. Синхронізація без втрат

- **Outbox:** прочитані deals спочатку пишуться в локальну SQLite (WAL, `synchronous=FULL`), лише потім відправляються; видаляються з черги після `2xx`. Інтернету немає хоч тиждень — нічого не губиться.
- **Перекриття вікна:** щохвилини читається історія за останні 7 днів (а не «з останньої угоди») — пізні/виправлені брокером deals теж приїдуть; сервер ідемпотентний, повтори безкоштовні.
- **Повна історія:** при першому підключенні рахунку — з 2000-01-01, пачками по 1000.
- **Нічна звірка:** раз на добу Bridge відправляє кількість і суму `profit` deals за 90 днів; сервер порівнює зі своїми даними й при розбіжності просить `resync`.
- Повтори: експоненційна затримка з jitter; `401` через годинник ПК → коригуємо зсув за заголовком `Date` сервера; `410/426` (стара версія) → оновлення.

### 5.3. Час брокера (ADR 0001)

MT5 віддає час угод як «годинник сервера брокера», замаскований під UTC. Тому:
- сервер зберігає сирий `time_msc` у `mt5_deals` і конвертує в UTC за `accounts.broker_timezone`;
- **основний спосіб — за історією барів (працює й у вихідні, і для минулих дат):** форекс-тиждень відкривається в неділю о 17:00 за Нью-Йорком, тож `зсув = час першого H1-бару тижня (сервер) − цей момент в UTC`. Bridge надсилає час першого бару кожного тижня для одного видимого форекс-символу (`copy_rates_range`); сервер отримує зсув на кожен тиждень і бачить правило переходу на літній час. Тижні, що починаються не в понеділок 00:00 (Різдво, Новий рік), відкидаються. Перевірено на ACG: §9.3;
- додатково — поточний зсув за свіжим тіком (`symbol_info_tick().time − UTC`, лише при відкритому ринку) як контроль;
- для автоствореного рахунку пояс обирається за цим зсувом; ACG Markets підтверджено живе за правилом «Нью-Йорк + 7 год» (GMT+2/+3 з переходом за датами США, §9.3) — для цього потрібен пояс-правило, якого немає в IANA (відкрите питання 3);
- якщо виміряний зсув розходиться з `broker_timezone` — плашка на сайті, а не тиха помилка.

### 5.4. Видимий статус (без «вічно зеленого»)

- Heartbeat раз на 60 с: версія, термінали, рахунки, баланс/equity, остання успішна синхронізація, коди помилок.
- На сайті: «Bridge: онлайн, синхронізовано 12 с тому» / «офлайн з 14:02» / «термінал не запущено». Під час відкритого ринку відсутність heartbeat > 10 хв — попередження на Головній.
- Трей-іконка: зелена / жовта (немає інтернету, дані в черзі) / червона (потрібна дія) + пункти «Відкрити MQVault», «Синхронізувати зараз», «Відкрити журнал подій», «Від'єднати цей ПК».

### 5.5. Видалення

Стандартне «Програми → Видалити»: прибирає автозапуск, ключ пристрою, outbox, логи; перед цим відкликає пристрій на сервері. Угоди в журналі лишаються.

## 7. План робіт

0. **Прототип (1–2 дні):** `initialize()` без налаштувань на чистій Windows з 3 брокерами; 2 термінали одночасно; вимір зсуву часу; збірка Nuitka + перевірка VirusTotal; ліцензія `MetaTrader5`. Без цього далі не йдемо.
1. **Сервер:** міграція (після погодження) → `signature`, `pairing`, `deals-to-trades`, `account-match` + тести → ендпоїнти → middleware-матриця.
2. **Bridge:** обгортка read-only, supervisor/worker, outbox, ключ (TPM → CNG → DPAPI), трей, AST-перевірки в CI.
3. **Інсталятор і оновлення:** Inno Setup per-user, Authenticode, minisign-маніфест, відкат.
4. **Сайт:** сторінка підключення, список пристроїв, статус на Головній, плашки зіставлення рахунків.
5. **Перевірка:** усі тести з розділу 4.3 зелені; тиждень на демо-рахунку з порівнянням із звітом MT5 (кількість угод і сума net збігаються до цента); лише потім — реальний рахунок власника.

## 8. Відкриті питання до власника

1. ~~**Невідомий рахунок**~~ — **вирішено 2026-11-08:** створювати автоматично (`personal`) і питати на Головній «це проп? / не синхронізувати».
2. **Сертифікат підпису коду:** без нього Windows SmartScreen показує «невідомий видавець» — це ламає «просто встанови». Варіанти: Azure Trusted Signing (~$10/міс, треба перевірити доступність для вашої країни/особи) або OV-сертифікат (~$200–400/рік).
3. ~~**Пояс брокера «NY+7»**~~ — **вирішено 2026-11-08:** додано значення `broker_timezone = "FX/NewYork+7"` (§9.4).
4. ~~**Коментарі угод MT5**~~ — **вирішено 2026-11-08:** не синхронізувати; сервер відхиляє пачку з полем `comment`.
5. **Відкриті позиції наживо** (`positions_get`) — у першій версії чи пізніше? Пропозиція: пізніше.
6. **Новини з MT5** (над якими зараз працюють окремо): Python API не дає доступу до економічного календаря MT5 — для нього потрібен MQL5, тобто налаштування в терміналі. Тому Bridge на першому етапі календар не передає; якщо джерелом новин стане MT5, канал Bridge (підписані запити) можна буде використати й для нього окремим пакетом.

### 9.1. Другий прогін — рахунок з угодами (2026-11-08)

### 9.3. Зсув часу брокера у вихідні й повнота історії (2026-11-08)

Підключений рахунок `ACGMarkets-Main` — **поточний проп-рахунок власника**; MT5 показує його як `trade_mode = demo`. Тому: (1) з нього лише читаємо, усе, що пише, тестуємо на окремому демо-рахунку; (2) проп не визначається автоматично (п. 3.7).

**Зсув часу за історією барів.** Журнал терміналу на цьому ПК не має днів угод (вони відкривались не з цього терміналу), тож зсув виміряно за першим H1-баром кожного форекс-тижня `AUDCAD.raw`, грудень 2025 – листопад 2026 (5 832 бари, 50 тижнів):

| Тижні | Перший бар (сервер) | Зсув | «NY+7» | EET (`Europe/Athens`, як Київ) |
|---|---|---|---|---|
| грудень – 1 березня | пн 00:00 | +2 | +2 ✓ | +2 ✓ |
| **8, 15, 22 березня** (США вже на літньому, ЄС ні) | пн 00:00 | **+3** | +3 ✓ | +2 ✗ |
| 29 березня – 18 жовтня | пн 00:00 | +3 | +3 ✓ | +3 ✓ |
| **25 жовтня** (ЄС уже на зимовому, США ні) | пн 00:00 | **+3** | +3 ✓ | +2 ✗ |
| з 1 листопада | пн 00:00 | +2 | +2 ✓ | +2 ✓ |

Збіг: «NY+7» — 48/50, EET — 44/50; обидві розбіжності «NY+7» — святкові тижні (26.12 і 02.01 торгівля відкрилась у п'ятницю), їх алгоритм відкидає. **Висновок:** ACG = «Нью-Йорк + 7 год». Угоди 27–31.10 мали зсув **+3**, а не +2 — з поясом `Europe/Kyiv` вони потрапили б у журнал на годину пізніше. Метод працює у вихідні й для будь-якої минулої дати — він і стає основним (п. 5.3). Ручні рахунки журналу зараз мають `broker_timezone = Europe/Kyiv`; якщо їхні брокери теж «NY+7», ручний ввід помиляється на годину в ці 4 тижні — це окреме питання, тут нічого не змінено.

**Повнота історії.** Сума `profit + commission + swap + fee` усіх deals (включно з депозитом) **дорівнює `account_info().balance` до цента** (різниця 0,00), відкритих позицій 0. Отже, `history_deals_get` повертає історію без пропусків — це стане нічною самоперевіркою Bridge (п. 5.2). Торгові підсумки: gross −485,81 · комісія −30,68 · своп −3,39 · fee 0 · **net −519,88 USD — власник звірив із вкладкою «Історія» терміналу: збігається** (2026-11-08).

**Ще не перевірено (потрібна ваша участь або робочий день ринку):**
1. Два й більше терміналів одночасно (на ПК встановлений один MT5) і інші брокери — зокрема реальний або проп-рахунок.
2. Часткові закриття, реверси (`inout`), `out_by` — у наявній історії їх немає.
3. Зсув часу в будній день (ринок відкритий).
4. SmartScreen на завантаженому файлі та інші антивіруси (після рішення щодо сертифіката / VirusTotal).
