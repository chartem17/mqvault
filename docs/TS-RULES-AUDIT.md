## 2. Правило ТС → що є → чого бракує

| Правило ТС | Що вже є | Чого бракує / що посилити |
|---|---|---|
| **Час усюди Europe/Kyiv** | `DEFAULT_TIMEZONE = Europe/Kyiv`; день — у поясі користувача (ADR 0001); сесії — за ринками (ADR 0002) | Вікна ТС задані київським годинником — окремо від ринкових сесій. Пояс ТС — параметр конфігу (за замовчуванням `Europe/Kyiv`), день лімітів ТС — у цьому ж поясі. |
| **Максимум 3 угоди на день** | `max_trades_per_day` (по стратегії, після факту); рядок на Головній | Перевірка **до входу** (бар'єр плану); рахувати й заплановані, ще не імпортовані входи; автопозначка порушення в угоди. |
| **2 стопи → блок до наступного дня** | `max_losses_per_day` — лише попередження | Справжній блок: план не зберігається до кінця дня; автопорушення для угод після ліміту. |
| **Вікна: ранок 09–12, ланч 12–14 без входів, NY 14:30–19, вечір/ніч заборонено** | `allowed_sessions` за ринковими сесіями (межі не збігаються: NY з 15:00 Києва, ланч Лондона інший) | Нові вікна в конфігу (початок/кінець/входи так-ні, будні дні); «зараз вікно чи ні, до котрої, наступне»; автопорушення «поза вікном». |
| **Базовий ризик 1 %; 3 збитки підряд → 0.5 %; назад після 2 прибуткових на 0.5 %** | Немає (є лише `risk_range` і `risk_escalation_after_loss`) | Автомат стану ризику з історії угод рахунку + пояснення «чому»; ризик у плані = поточний стан; автопорушення «ризик не за правилом». |
| **Ризик > 1 % лише як добір або метали (ліміт лотажу), з прапорцем** | `high_risk_requires_rr` (інша логіка) | Прапорець у плані й в угоді: `add_on` (основна в беззбитку) / `metal_lot`; без нього ризик > бази — порушення. |
| **Немає входів на 0.7 / 0.5 «бо невпевнений»** | — | Ризик плану не вибирається вручну: лише значення стану (або позначений виняток). |
| **Модель входу** (контекст 1H/4H, POI з повним зняттям, зняття за фракталом, реакція FVG, бос тілом M5/M15, лімітка на FVG, M3 лише для уточнення) | `model_confirmation` — одна ручна галочка; чипи сетапів | Чекліст плану з обов'язковими полями для кожного кроку; вибір ТФ боса лише M5/M15; прапорець «M3 — лише уточнення»; текст правил на сторінці Playbook (з визначенням фрактала). |
| **Стоп за екстремум зняття; ціль — рівень; RR ≥ 2** | `min_planned_rr` після факту з SL/TP угоди | Ціни в плані, RR рахує система (і сервер) і блокує < 2; перевірка сторін (стоп/ціль з правильного боку). |
| **Ведення: стоп або тейк; часткові рідко; БУ лише після 1–1.5R у проблемній зоні; таргет не переносити** | Чип помилки «Moved stop», «Early exit» | Причини порушення в угоді: перенесений таргет (авто: TP угоди далі за ціль плану; вручну), ранній БУ, часткова фіксація (вручну). |
| **Застій: тримати до SL/TP, не закривати вручну в 0; тег «застій»** | Немає тегів | Тег «застій» в угоді (`meta.discipline.stagnation`); автопорушення «ручне закриття в 0» з `meta.bridge.close_reason = manual` і |R| < 0.1; для CSV — вручну. |
| **Чекліст-бар'єр до входу** | Денний чекліст без блокування | Новий об'єкт «план угоди» (таблиця `trade_plans`), створюється ДО входу; 12 обов'язкових пунктів; кнопка неактивна з переліком блокерів; **сервер перевіряє все повторно** (без обхідних шляхів через API). |
| **План ↔ реальна угода** | Немає | Автозіставлення (рахунок, символ без суфікса брокера, напрямок, час входу в межах плану, ціна входу в допуску від відстані до стопу), один план — одна угода; ручне прив'язування на плані. На льоту (як ADR 0014), тож імпорт CSV і Bridge **не змінюються**. Угода без плану → «поза планом». |
| **Позначки дисципліни в угоді** | `meta.review.followed_plan` (ручна) | `meta.discipline` (ручні причини, «застій», «добір/метали»); автоматичні причини — на льоту. «За планом» = є план і немає порушень. Стара ручна позначка не губиться. |
| **Метрики дисципліни вище за P&L** | Тижневий звіт: розібрано / за планом (ручна) | Блок на Головній над P&L: % угод за планом за тиждень і місяць, результат «за планом» проти «поза планом», кількість і результат «застою». |
| **Числові параметри в одному місці** | Ліміти розкидані по правилах кожної стратегії | Один конфіг Playbook у `app_users.preferences.playbook` (санітизація, значення за замовчуванням у `lib/playbook/config.ts`), редагування на сторінці Playbook. |

## 3. Рішення й розвилки (для PR)

1. **Де живе конфіг ТС.** Обрано `app_users.preferences.playbook` — один на користувача, без міграції, із санітизацією. Альтернатива — нові типи правил у `strategy_rules` (по рахунку). Стратегії лишаються інструментом аналізу після факту; дублювання лімітів (3/2, RR 2) зі стратегіями — свідоме, до рішення власника: варіант «Playbook заповнює правила стратегії рахунку» — пізніше.
2. **Ліміти дня й стан ризику — по рахунку** (як стратегії). Якщо власник копіює одну угоду на кілька проп-рахунків — це правильно; якщо ні — додати перемикач «по всіх рахунках».
3. **Вікна ТС у київському часі проти ADR 0002** (сесії за ринками). Не суперечить: це окремі «торгові вікна» ТС з явним поясом у конфігу, ринкові сесії не змінюються. День лімітів ТС — у поясі ТС (за замовчуванням збігається з поясом користувача).
4. **Збереження планів** — нова таблиця `trade_plans` (міграція в репо, **не застосована**; потрібне погодження власника). Без неї сторінка показує «міграцію не застосовано», решта працює.
5. **Скрін** — посилання (TradingView/зображення), як `screenshot_url` угоди; завантаження файлів на сайті немає.
6. **Беззбиток у серії збитків** не рахується ні збитком, ні прибутком (|R| < 0.1). «2 прибуткові на 0.5 %» — сумарно, не обов'язково підряд. Обидва — параметри конфігу.
